# Ghita Agent v1.2.0 — Master Plan (3 demo → 5 beta → chính thức)

> **For agentic workers:** Master plan điều phối chu kỳ phát hành theo cấu trúc **mốc → track → phase**. Khi bắt đầu một mốc, track của mốc đó được viết thành plan chi tiết riêng (bite-sized tasks, TDD) tại `docs/plans/2026-08-30-v1.2.0-<tên-mốc>.md` — mỗi track thành 1+ task, mỗi phase thành các step có checkbox. Plan này là bản đồ tổng + ràng buộc chung.

**Goal:** Phát hành v1.2.0 chính thức qua 9 cột mốc (3 demo + 5 beta + chính thức), bản chính thức đạt: Rust hóa + tối ưu tài nguyên, tăng tốc phần cứng, hiệu quả app cao nhất.

**Architecture:** Tại thời điểm kế hoạch — repo gồm 7 crates Rust (`tokenizer, secscan, sandbox, store, docloader, codegraph, retrieval`), 28 packages TS (`agents, ai-engine, mcp, skills, memory, native-bridge, security, quotas, relay-server, computer-use, browser-control, voice, ...`), 3 apps (`desktop` Tauri, `mobile` React Native, `vscode-extension`). Nhánh chính `main` = `bc8591d` (v1.1.5-debug), version `1.1.5`. Kho tham khảo `refer_project/` có ~60 dự án đã clone theo nhóm `ai-core / ai-framework / ai-tools / browser / desktop / infra / memory`.

**Tech Stack:** TypeScript + Vite + React (desktop), React Native (mobile), Rust + napi-rs (native addon qua `native-bridge`), Vitest + turbo, Cargo workspace, Tauri 2 + NSIS.

**Spec:** Yêu cầu của owner ngày 2026-08-30 (nội dung từng mốc đã decode từ yêu cầu gốc) + quy ước track/phase kế thừa chu kỳ 1.1.5 (7 track, phase đánh dấu P<t>.<n>).

## Global Constraints

- **QUY TẮC VĨNH VIỄN của owner (2026-08-31):**
  1. Trong quá trình làm **KHÔNG commit, KHÔNG push** — bất kể git local hay GitHub remote. Mọi thay đổi giữ ở working tree.
  2. **Mỗi phiên bản làm trên NHÁNH RIÊNG** (vd `v1.2.0-demo1`, `v1.2.0-beta1`...) tách từ `main` để dễ quản lý. Khi xong và **chỉ khi owner yêu cầu**: gộp nhánh vào `main`, rồi mới commit/push (push cũng phải owner yêu cầu riêng).
- Working tree phải sạch trước khi bắt đầu mốc mới (trừ docs/plans).
- Gates bắt buộc sau MỖI phase có sửa code: `pnpm typecheck` 44/44, `pnpm lint --concurrency=1` 43/43, `turbo test` 44/44, `knip`, `audit-security` (baseline 44 không tăng), `cargo test` workspace + `clippy --all-targets --all-features -D warnings` 0 warning (thêm `-p X --features addon --all-targets` cho crate có addon), desktop smoke 4/4, e2e 4/4, coverage T0/T1, evals gate.
- Rust: mọi sửa tay phải `cargo fmt` trước khi coi là xong; máy owner dùng toolchain `stable-x86_64-pc-windows-gnu` — build.rs manifest comctl32 phải giữ nguyên.
- File CI-consumed KHÔNG xóa: `docs/code-review-findings.md`, `docs/perf-*.json`, `docs/resource-budget.json`, `docs/coverage-tiers.json`.
- Bulk edit file hàng loạt chỉ dùng TS Compiler API (không regex state-machine).
- Mọi tính năng native phải giữ JS fallback (pattern hiện có: `getNativeCosine()?.() ?? js()`), addon code phải test được cả 2 nhánh.
- Version bump chỉ diễn ra khi owner ra lệnh; `sync-version` phải đồng bộ toàn monorepo.
- Tham khảo từ `refer_project/` CHỈ để nghiên cứu ý tưởng + API pattern; KHÔNG copy code có license không tương thích — ghi nguồn + license vào mỗi mục nghiên cứu.

## Quy ước track/phase (áp dụng mọi mốc)

- **Track (T<t>)** = một chủ đề công việc tương đối độc lập trong mốc (VD: T1 Ổn định, T2 Thuật toán, T3 Rust hóa, T4 Publish). Track chạy tuần tự, trừ khi ghi chú song song được.
- **Phase (P<t>.<n>)** = một bước có tiêu chí xong (done-criteria) riêng trong track; hoàn thành phase mới qua phase sau. Mỗi phase kết thúc chạy gates (nếu có sửa code) hoặc kiểm tra sản phẩm riêng (doc/catalog/test).
- **Track cuối mỗi mốc luôn là Track Publish (T_publish)**: chốt CHANGELOG → gates tổng → owner review → owner ra lệnh commit/tag. Không có lệnh = dừng chờ.
- **Đầu mỗi mốc**: tạo nhánh phiên bản từ `main` (vd `git checkout -b v1.2.0-demo1`) — toàn bộ phase của mốc chạy trên nhánh đó, không commit; cuối mốc khi owner yêu cầu mới gộp vào `main` rồi commit/push.
- Khi viết plan chi tiết của mốc: mỗi track = 1+ task, mỗi phase = các step (viết test → chạy fail → implement → chạy pass → commit khi được lệnh).
- Owner điều khiển track-by-track như chu kỳ 1.1.5; có thể dừng/đổi phạm vi ở ranh giới track hoặc phase.

## Tiến trình & rủi ro

**Thứ tự bắt buộc:** demo1 → demo2 → demo3 → beta1 → ... → chính thức. Mỗi mốc nghiệm xong mới qua mốc sau; owner điều khiển track-by-track, có thể dừng/đổi phạm vi ở ranh giới track/phase.

**Rủi ro chính:**

1. **Scale beta1/beta4 (50+50 tính năng)** — giảm thiểu: catalog owner duyệt trước (P1.3), chia batch, tính năng L có thể cắt ở ranh giới batch.
2. **"100% không lỗi" demo1** — giảm thiểu: feat-matrix là định nghĩa vận hành được của "100%"; bug phát hiện sau → ghi matrix và sửa ở mốc kế tiếp.
3. **License** khi học từ refer_project — bắt buộc ghi license từng nguồn; chỉ lấy ý tưởng/pattern.
4. **Windows máy owner dưới tải nặng** (SIGABRT/fork fail/os error 1455) — gates `--concurrency=1`, serial, retry sau sleep.
5. **Security regression** khi thêm device control/API mode — P3.3/P3.4 beta5 + audit-security mỗi lần đụng.

**Quy ước review mỗi mốc:** kết thúc mốc → owner review working tree (`git diff`, VS Code Source Control) → owner ra lệnh commit/tag chính xác → mới chuyển mốc. Không có lệnh = dừng lại chờ.
